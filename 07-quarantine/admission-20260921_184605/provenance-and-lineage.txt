--- protein/11-molecules/BEAD-ARCHITECTURE.md ---
# Bead / Molecule Chain

## Canonical roles

- `12-runtime/state/folding.state` is the authoritative source state.
- `12-runtime/state/molecule.state` is derived runtime bookkeeping.
- `11-molecules/live.molecule` is the current materialized molecule.
- `04-relation/protein-relation.state` is the authority for relationships.
- `BEADS` is a derived counter, not a source of truth.
- `06-promoter/bead-promotion/` is the canonical mutation boundary.

## Lifecycle

```text
source
  -> collect
  -> classify
  -> relate
  -> validate
  -> promote
  -> materialize
  -> derive runtime state
  -> evidence
```

## Important boundary

The current `folding.state` is state bookkeeping. It must not be described as
a computational folding engine until an actual computation, validation, and
evidence chain exists.

## Bead types

The architecture reserves 20 type slots:

```text
type-01 ... type-20
```

Fibers operate on the generic bead abstraction and must not hard-code the 20
types.

## Reconciliation

If the bead counter disagrees with canonical state, do not manually adjust the
counter. Reconcile:

```text
folding.state
-> molecule.state
-> live.molecule
-> relation
-> evidence
```

Then regenerate derived state.

BEAD TYPE REGISTRY

This directory contains the definitions for the supported bead types.

The architecture reserves type-01 through type-20 without requiring the
execution fibers to hard-code individual types.

Each type should describe:
- type identifier
- canonical name
- source/derivation
- validation requirements
- relation metadata
- evidence requirements

Do not create a type directory merely to increase the counter. A type becomes
active only when a validated canonical definition exists.

--- protein/06-promoter/bead-promotion/README ---
BEAD PROMOTION BOUNDARY

Role:
Promote validated bead/molecule changes into canonical Protein state.

Required flow:
RECEIVED -> CLASSIFIED -> RELATED -> VALIDATED -> PROMOTED

Rules:
- Do not edit folding.state directly as a promotion shortcut.
- Do not increment BEADS directly.
- Preserve source and hash evidence for every promotion.
- Update relation state before declaring promotion complete.
- Derived counters must be reconciled from canonical state.

This directory defines the boundary; executable promotion logic may be added
after the current implementation is inventoried and verified.
